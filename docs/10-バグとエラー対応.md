# 10 - バグとエラー対応（対応プレイブック）

`docs/07` が「症状 → 原因」の早見表なのに対し、本書は
**バグ/エラーにどう向き合い、どう切り分け、どう直して、どう報告するか**の手順書。
原因が表にないとき・再現が不安定なときはここに従う。

## 0. 鉄則

- 推測で直さない。**まずログ/スタックトレースを読む**
- 一度に複数箇所を変えない。**1変更 → 検証**（原因を局所化できる）
- 直したら必ず `docs/09` STEP 4 の検証を回す
- 検証できていないことを「直った」と書かない（`CLAUDE.md` §4・§8）
- 曖昧／大規模リファクタが要る／アーキテクチャに影響 → **直さず確認**

## 1. まずエラーの「層」を判定する

| 層 | 出る場所 | 例 | 主参照 |
|---|---|---|---|
| **ビルド失敗** | `./gradlew build` の出力 | プラグイン未解決 / 依存解決失敗 / コンパイルエラー / toolchain | §2, `docs/07` ビルド系 |
| **起動失敗（クラッシュ）** | `run/crash-reports/` と `run/logs/latest.log` | registry not present / mods.toml 不正 / side 違反 | §3〜§4 |
| **起動はするが挙動が変** | `run/logs/latest.log`（debug.log） | 紫黒テクスチャ / 名前未翻訳 / ドロップしない | §5, `docs/07` 表示系 |
| **データ駆動エラー** | latest.log / `runData` 出力 | レシピ・loot・タグの JSON 不正/参照ミス | §6, `docs/06` |

層を取り違えると的外れな修正になる。**必ず最初に層を確定**する。

## 2. ビルド失敗の読み方

```bash
./gradlew build --stacktrace      # 例外の発生箇所
./gradlew build --info            # さらに詳細（依存解決など）
./gradlew build --debug           # 最終手段（大量出力）
```

- `* What went wrong:` の直後が要点。`Caused by:` を最後まで追う
- コンパイルエラーは `javac` のメッセージ＋ファイル:行。多くは API 名違い（`docs/03` のマッピング/レジストリ早見）
- 「Plugin not found」「Could not resolve forge」は**ほぼネットワーク遮断**。
  `curl -s -o /dev/null -w "%{http_code}" https://maven.minecraftforge.net/net/minecraftforge/forge/maven-metadata.xml`
  が 403/000 なら遮断 → 直す対象は**コードではなく環境**。その旨を報告する（`docs/07` 末尾）

## 3. クラッシュレポートとログの場所

開発実行の作業ディレクトリは `build.gradle` で固定:
- クライアント/サーバ: `run/`
- data 生成: `run-data/`

| ファイル | 用途 |
|---|---|
| `run/crash-reports/crash-*.txt` | クラッシュ時の整形レポート（最重要） |
| `run/logs/latest.log` | 直近の実行ログ全体 |
| `run/logs/debug.log` | 詳細ログ（`build.gradle` で `console.level=debug` 指定済み） |

クラッシュレポートの読む順:
1. `Description:` … 何の最中に落ちたか（init / rendering / tick 等）
2. 最初の例外と **`Caused by:` の連鎖の最深部**（根本原因はたいてい一番下）
3. `-- MOD <modid> --` … 起因 Mod
4. スタックの中の `com.example.examplemod...` 行 = 自分のコードの該当箇所

`build.gradle` で `forge.logging.markers=REGISTRIES` 済み。登録順の問題追跡に使える。

## 4. Forge 特有のクラッシュ・パターン

| メッセージ/症状 | 根本原因 | 対処 |
|---|---|---|
| `Registry Object not present` / NPE が `<clinit>` 付近 | クラスロード時に `RegistryObject.get()` を呼んだ | `.get()` は**使用時のみ**。フィールド初期化や static で呼ばない（`docs/03`） |
| `Encountered errors during registry` | DeferredRegister 未接続 / 名前重複 | `ExampleMod` で `ModXxx.REGISTER.register(modEventBus)` 済みか。レジストリ名の重複なし |
| エンティティのスポーン/`/summon` で NPE（attribute / `getAttribute` 系） | `EntityAttributeCreationEvent` 未登録 | `ExampleMod` で `event.put(<EntityType>, ...createAttributes().build())`（`docs/03`/`docs/epicfight/12`） |
| エンティティが透明 / 描画で `IllegalArgumentException` | レンダラ未登録 / モデルレイヤ不一致 | `EntityRenderersEvent.RegisterRenderers`（MOD バス・client）で登録（`client/`・`docs/03`） |
| `Mod file ... missing mods.toml` / TOML parse error | `mods.toml` 破損・トークン手書き | `${...}` は触らない（build が置換）。`docs/02` |
| dedicated server で `NoClassDefFoundError`（client クラス） | クライアント専用 API をサーバ経路で参照 | クライアント専用処理は `FMLClientSetupEvent`/`DistExecutor` に隔離（`docs/03`） |
| `Missing or unsupported mandatory dependencies` | `mods.toml` の依存 versionRange 不整合 | `gradle.properties` のレンジを確認（手書きしない） |
| 起動直後 toolchain/Java 系で停止 | JDK17 不在 | `./gradlew -q javaToolchains`（`docs/01`） |

切り分けの基本: **「構築フェーズ（@Mod 構築・登録）」で落ちたか「ゲーム中」で落ちたか**を
Description とスタックで判定 → 前者は登録コード、後者はイベント/ロジックを疑う。

## 5. 「起動するが変」系（クラッシュしない不具合）

クラッシュしないので **latest.log の WARN/ERROR を grep** する:

```bash
grep -nE "WARN|ERROR|Exception|Unable to load|Missing" run/logs/latest.log | tail -40
```

| 症状 | 確認 |
|---|---|
| 紫黒（missing texture/model） | モデル JSON とテクスチャの**名前空間 `examplemod:` とパス**一致（`docs/04`/`05`/`06`） |
| 名前が `item.examplemod.x` のまま | `lang/en_us.json` と `ja_jp.json` の**両方**にキー（綴り厳密一致） |
| ブロックを壊しても無ドロップ | `data/.../loot_tables/blocks/<name>.json` 有無/名前 |
| クリエイティブに出ない | `ModCreativeTabs` の `displayItems` に `output.accept(...)` |

これらは「仕様どおりに静かに無視される」ため、ログ警告が唯一の手がかりになることが多い。

## 6. データ駆動（recipe / loot / tag）エラー

- 構文エラー → latest.log に `JsonSyntaxException` / `com.google.gson...`。
  まず `for f in $(find src -name '*.json'); do python3 -m json.tool "$f" >/dev/null||echo BAD:$f; done`
- 参照エラー（存在しないアイテム id 等）→ ログに該当 recipe/loot のパスが出る。
  `examplemod:` と `minecraft:` の名前空間取り違いが多い（`docs/06`）
- バニラのタグへ追記する場合は **`data/minecraft/...`** 配下（`docs/06` §tags）
- 生成物を疑うなら `./gradlew runData` の出力と `src/generated/resources` を確認（ネットワーク必要）

## 7. 再現と切り分け

1. **再現手順を1つに固定**（どの操作で・client か server か・毎回か）
2. **直近の変更を疑う**: `git diff` / `git stash` で戻して再現するか確認
3. 戻して直る → その差分が原因。**最小単位**に分割して 1 つずつ戻す
4. 戻しても再現 → 既存バグ。層判定（§1）からやり直す
5. 単一開発フローのため `git bisect` より「直近差分の revert/stash」が速い

## 8. 修正後の必須再検証（順番厳守）

`docs/09` STEP 4 と同一:

```bash
for f in $(find src -name '*.json'); do python3 -m json.tool "$f" >/dev/null 2>&1 || echo "BAD JSON: $f"; done
grep -n modId src/main/resources/META-INF/mods.toml
./gradlew --version                 # Gradle 8.1.1
./gradlew build                     # ネットワーク開放時のみ
./gradlew runClient                 # GUI 環境のみ（headless は不可）
```

直した症状が**実際に消えたこと**を確認するまで完了としない。

## 9. 報告フォーマット

- **層**（ビルド / クラッシュ / 挙動 / データ）と**根本原因**（推測でなく根拠＝ログ該当行）
- 変更したファイルと修正内容
- 再検証でどこまで確認できたか（(JSON/id/wrapper) は常時可、(build/runClient) は環境依存）
- 確認できない項目は「未検証」と明記
- ネットワーク遮断が原因なら「コードではなく環境」と切り分けて報告（`docs/07` 末尾）

## 10. エスカレーション（直さず確認するケース）

- 原因が複数解釈できる／修正方針が一意でない
- 大規模リファクタ・アーキテクチャ変更を伴う
- 仕様意図が不明（その挙動がバグか仕様か判断できない）

→ 勝手に進めず、状況・原因候補・選択肢を添えて確認する（`CLAUDE.md` §8）。
